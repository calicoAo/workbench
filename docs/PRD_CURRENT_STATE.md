## 2. 产品概述

### 2.1 产品定位

Personal Workbench 是面向个人长期使用的现实生活管理系统。它把任务执行、时间记录、项目、习惯、生活记录、文字沉淀、成长反馈和个人财务放在同一个工作台中，但每个领域仍保留独立的数据真值。

产品的核心不是“建立更多清单”，而是形成以下闭环：

```text
想做什么
→ 发布任务或捕捉想法
→ 选择今天真正要做的事
→ 计时或补录真实投入
→ 完成任务并保留历史事实
→ 在项目、成长、文字和财务视角中回看
→ 决定下一步行动
```

当前产品采用“悬赏”作为任务体验语言，但悬赏仍然使用 Task 数据模型，不存在独立的多人任务市场、抢单系统或真实货币奖励。

### 2.2 核心价值

| 用户问题 | 产品回答方式 |
| --- | --- |
| 我今天真正要做什么？ | Today、今日接取、重点任务、待续接 |
| 我现在在做什么？ | 全局单一计时会话、跨页面 Mini Timer |
| 我实际投入了多少时间？ | Timer Segment、手工 Actual、Timeline |
| 一件长期事务推进到哪里？ | Project、Task 进度、项目投入与材料 |
| 哪些行为正在形成习惯？ | Habit 规则、目标、发生记录与跳过状态 |
| 最近的生活状态如何？ | Sleep、Water、晨写、日记与历史回看 |
| 值得保留的想法在哪里？ | Quick Notes、灵感库、标签和项目关联 |
| 我的长期积累是什么？ | XP、等级、成长维度、投入分布与最近来源 |
| 我的钱发生了什么？ | 账户、流水、预算、周期收支、报表与对账 |
| 数据能否被找到和带走？ | 全局搜索、领域导出、财务备份、回收站 |

### 2.3 目标用户

当前主要用户是希望长期记录和管理个人生活的单人用户，典型特征包括：

- 同时维护工作、学习、创作、健康和生活事务；
- 不满足于待办事项，需要记录真实投入与历史变化；
- 希望把碎片想法、复盘文字和行动计划连接起来；
- 需要轻量但可核对的个人财务账本；
- 接受游戏化反馈，但不希望游戏化阻碍正常使用；
- 重视个人数据的可追溯、可导出和明确归属。

账号系统支持注册和登录，但当前产品仍是个人工作台，不提供组织空间、共享项目、多人协作或权限角色体系。

## 3. 产品目标与非目标

### 3.1 当前目标

1. 让用户可以每天完成“选择任务—开始行动—记录投入—结束或完成—回看结果”的闭环。
2. 让 Task、Project、时间投入、Habit、Writing、Finance 各自拥有唯一可解释的事实来源。
3. 让刷新、切页、重试和并发操作不会产生重复时间、重复奖励或单边财务记录。
4. 让移动端可以快速完成任务、记录时间、喝水、写随手记和记账等高频动作。
5. 让历史记录能够被搜索、导出、恢复或追溯，而不是只服务当天界面。
6. 让成长和 AI 能力消费已有事实，但不替代领域数据或自动决定用户行为。

### 3.2 当前非目标

以下内容不属于当前已交付产品范围：

- 多人协作、团队项目、任务抢单或社交关系；
- 银行直连、真实支付、证券交易、投资建议和税务系统；
- 外部 Agent 直接获得全量数据或未经确认写入真实任务；
- 自动把所有想法、日记或灵感转换成 Task；
- 用 XP、金币或成长分替代真实财务金额；
- 通用知识库、通用工作流引擎、通用插件市场；
- 完整医疗健康平台或医学诊断；
- 复杂离线同步和多端实时协作；
- Inventory、外部 Agent Bridge、Agent Wallet 等尚未实施的扩展域。

## 4. 当前交付状态

状态定义：

- **已实现**：前后端主路径和对应数据能力已经存在，并有聚焦测试或集成测试覆盖；
- **已实现，待收尾**：核心能力可用，但视觉资源、完整验收或周边体验仍需补齐；
- **局部实现**：已有可用功能，但尚未形成规划中的统一平台或完整闭环；
- **待实施**：当前没有可作为正式产品能力使用的完整实现。

### 5.2 移动端结构

移动端固定五个主入口：

```text
今日 / 任务 / 日历 / 文字 / 设置
```

项目、生活、财务、成长、奖励、工具和搜索通过更多入口或页面内深链进入。全局 Quick Action 提供高频动作：

- 发布任务；
- 记录随手记；
- 启用的首个 Writing Slot；
- 记录饮水；
- 记支出；
- 安排计划；
- 补录实际；
- 记录睡眠；
- 记收入；
- 转账。

## 6. 核心用户流程

### 6.1 每日执行闭环

```text
进入 Today
→ 查看当前专注、今日任务和待续接
→ 接取已有任务，或发布新任务
→ 开始计时
→ 暂停/继续，或结束本次投入
→ Timeline 写入真实时间
→ 用户显式决定是否完成任务
→ 奖励和成长读取已提交事实
```

关键要求：

1. 接取任务不自动开始计时；
2. 结束计时默认不完成 Task；
3. 完成 Task 可以不虚构时间；
4. 补录实际默认不完成 Task；
5. 刷新或切页后，当前计时从服务端恢复；
6. 同一用户只能存在一个未结束 Session；
7. 暂停期间不计入真实投入；
8. 跨日投入按实际日期拆分并保留来源。

### 6.2 想法到行动

```text
Quick Action 新建随手记
→ 仅正文也可保存
→ 可补标题、标签或关联项目
→ 可继续作为个人文字保存
→ 可加入灵感库整理
→ 需要行动时显式转成 Task
→ 原文和来源关系继续保留
```

产品不得自动把所有 Quick Note 转成任务，也不得因转 Task 而删除或覆盖原文。

### 6.3 项目推进

```text
创建 Project
→ 在项目中查看/创建 Task
→ 接取并执行 Task
→ 时间投入按发生时项目归属进入项目统计
→ Quick Note 可作为项目素材
→ 项目完成或归档时显式处理未完成 Task
```

任务后来移动项目，不得改写已经发生的历史投入归属。

### 6.4 Habit 与生活记录

```text
创建 Habit 定义
→ 设置频率与目标
→ 到期日显示在 Routines / Today
→ 完成、记录数量或跳过
→ 历史按当时生效的规则解释
```

Sleep、Water、晨写等专用领域不重复写入通用 Habit 真值。可以在同一页面组合呈现，但不能为了统一界面建立第二份事实。

### 6.5 文字与灵感

```text
用户在设置中选择启用的 Writing Slot
→ 在文字页进入晨写、日记或股市复盘
→ 按选择日期保存独立正文
→ 可从灵感库插入内容
→ 可主动请求 AI 分析
→ 历史归档保持可访问
```

AI 分析结果不能覆盖用户原文。AI 未配置或调用失败时，正文编辑和保存仍必须可用。

### 6.6 财务闭环

```text
初始化财务分类
→ 创建账户和期初余额
→ 记录收入/支出，或执行转账
→ 余额由有效 Entry 派生
→ 退款、更正、冲正保留审计关系
→ 预算和报表读取同一账本
→ 周期收支先生成待确认项，确认后才入账
→ 导入先预览和校验，确认后幂等入账
```

财务金额使用整数分。Workbench Coins、真实财务和未来外部 Agent Wallet 永久分账。

### 6.7 新用户引导

新注册用户获得版本化的核心循环引导：

```text
发布一个真实任务
→ 完成任务内容创建
→ 接取任务
→ 开始一次真实计时
```

引导只观察并推进真实业务事实，不创建教学假数据，不拥有 Task 或 Timer 状态。用户可以跳过，并可在设置中重启。

## 7. 详细功能需求

### 7.1 Task 与 Assignment

- Task 保存长期生命周期、标题、描述、类别、项目、预计时长、进度、截止时间和版本。
- Assignment 表示某个业务日期主动选择推进的 Task，不等于 Task 本身状态。
- 用户可以发布、发布并接取、编辑、接取、释放、设置重点、完成、重开和归档。
- 今日任务选择和排序必须使用显式写命令；读取 Today 或历史日期不得偷偷创建接取记录。
- 历史未完成项以待续接候选呈现，用户可以续接、延后、重新安排或不再提醒。
- 完成 Task 可以选择同时结束当前计时，也可以在没有计时的情况下直接完成。
- 重开后再次完成可生成新的完成事件，但首次完成奖励不得重复发放。

### 7.2 Timer、Timeline 与 Calendar

- 计时支持开始、暂停、继续、结束和取消。
- 一个 Session 可以包含多个 Segment；真实投入只计算关闭的有效片段。
- Timer 产生的 Timeline 投影是只读可追溯记录，不能通过普通 Schedule 编辑绕过 Timer 语义。
- 手工 Actual 支持关联 Task、项目和分类；默认只增加实际投入。
- 手工 Actual 与已有投入重叠时必须提示，用户可以调整或明确保存为不计入汇总的附注。
- Calendar 日视图支持编辑计划和手工实际；周、月、年视图提供范围回看。
- Timeline 明确区分计划、计时实际、手工实际、历史实际、睡眠和饮水时间点。

### 7.3 Projects

- Project 支持创建、编辑、状态变化、完成和归档。
- Project 详情组合任务、计划、ActualTime、投入和进度，不建立项目专用的第二套 Task。
- Project 完成前，如果仍有未完成 Task，必须让用户明确选择处理方式。
- Quick Note 可以关联一个 Project，并在 Project 素材区以摘要和深链呈现。
- 归档 Project 保留历史关联；新关联只能选择当前用户的有效 Project。

### 7.4 Habits、Sleep 与 Water

- Habit 支持每天、指定星期和每周 N 次规则。
- 规则和目标使用生效版本解释历史，不用当前设置覆盖过去。
- Habit 支持完成、数量/时长记录、跳过、停用、归档和恢复。
- Habit 可以关联 Task，但 Task 完成只通过领域公开能力写入对应发生记录。
- Sleep 按醒来日期归属，支持跨日睡眠区间。
- Water 支持杯数、实际饮水时间点和基于睡眠节奏的提示；允许超过推荐杯数继续记录。

### 7.5 Writing、Quick Notes 与 Inspirations

- 晨写、日记和股市复盘是三个独立 Writing Slot，新用户默认全部关闭，由用户显式启用。
- 关闭 Writing Slot 只移除主要入口，不删除历史，不影响搜索、归档和导出。
- Quick Note 只要求正文即可保存，支持版本冲突保护、归档、软删除和恢复。
- Quick Note 转 Task 必须由用户确认任务标题和发布方式；一次来源只能产生一个稳定关联 Task。
- Quick Note 引用 Journal 只进入当前草稿，不直接代替用户保存日记。
- Inspiration 复用 Quick Note 的标题、正文、日期和 Project 关系，只拥有收藏、置顶、归档和标签元数据。
- 标签筛选使用明确标签关系，不自动把正文中的 hashtag 当作分类真值。

### 7.6 Growth 与 Rewards

- Rewards 保存事件账本、XP、金币和兑换记录。
- Task、Timer、Writing、Decision 等领域在自己的事务或工作流中触发奖励，但 Rewards 不决定领域操作是否成功。
- 用户可以隐藏奖励界面；隐藏不停止奖励结算，也不影响 Task、Timer 和 Timeline。
- Growth 读取 Rewards 等级，并按 ActualTime 的发生时分类映射统计 7/30/90 天投入。
- Growth 维度由用户配置；分类可以不映射，未映射投入必须单独显示，不能丢失或强行归类。
- 当前 Growth 表达的是投入分布和行为事实，不是人格测试或客观能力认证。
- Pixel Visual 只是一层呈现资源，不得改变表单、导航、数据模型或业务真值。

### 7.7 Finance

- Account 支持现金、银行、支付和信用等类型，余额只能由有效 Entry 派生。
- 收入、支出、转账、退款、更正、冲正和作废必须保留交易关系与审计痕迹。
- 同币种转账使用一笔 Transaction 下的双边 Entry；本金不计入收入或支出。
- 退款按原支出分类抵减支出，不伪装成普通收入。
- Budget 支持月总预算和支出分类预算，超支只提示，不阻止真实记账。
- Recurring 先生成待确认 Occurrence；未确认项不改变余额。
- Report 必须读取同一账本，不维护第二套余额或收支累计。
- Import 经过文件摘要、来源行身份、字段预览、错误提示、重复识别和用户确认。
- Finance 导出和恢复属于敏感操作，需要用户主动发起；恢复前先校验数据图和余额一致性。

### 7.8 Search、Export、Trash 与 Settings

- Search 支持关键词、类型、日期范围、游标分页和领域深链。
- Search 当前覆盖 Task、Project、Habit、Quick Note、Journal、Morning Writing、Schedule 和 Finance。
- 通用 Export 按领域主动生成 JSON/CSV；Writing 额外支持 Markdown。
- Calendar 导出不得同时重复导出 Timer 投影和 Timer Segment 导致时间双算。
- Trash 是恢复能力的组合面，不拥有通用删除真值；当前只开放 Quick Note。
- Settings 管理个人资料、时区、分类、Writing Slot、语言、字体缩放、减少动效、奖励展示和数据入口。
- 修改时区只影响新记录默认值，不重写已有记录的业务日期。

### 7.9 AI 与 Decision Tools

- 当前 AI Writing Insight 只分析用户主动提交的晨写或日记，返回摘要、情绪标签、能量评分、压力关键词和建议。
- 当前 Psychological Bridge 根据目标和阻力生成桥梁文本、最小下一步和安抚语。
- AI 结果必须经过结构校验后保存；模型不可用时返回明确错误。
- 当前实现直接调用配置的 OpenAI-compatible Responses API，尚未形成统一 Provider Gateway、预算、成本遥测和 Artifact 生命周期。
- 决策记录和 AI 结果不能自动修改 Task、Project、Finance 等业务事实。

## 8. 核心产品规则

1. **接取不等于开始。** Assignment 只表达某天选择推进。
2. **计时不等于完成。** 结束本次默认只结算真实投入。
3. **进度不等于时长。** 实际投入不会自动换算 Task 百分比。
4. **计划不等于实际。** 计划到期或完成不会自动生成真实时间。
5. **同一用户只有一个未结束 Session。** 运行和暂停都占用当前执行槽。
6. **历史事实不随当前关系漂移。** 投入保存发生时项目、分类、日期和时区。
7. **读取不产生业务写入。** Dashboard、Search、Growth 和 History 读取不能偷偷结转或初始化领域事实。
8. **一次动作一个 operationId。** 同 ID 同参数可回放，同 ID 换参数必须冲突。
9. **跨表不变量由单一工作流和数据库事务负责。** 不能用多个独立请求拼装原子动作。
10. **用户数据按 userId 隔离。** 所有用户资源读写必须鉴权并限定当前用户。
11. **金币、真实财务、外部钱包分离。** 任一账本变化不得隐式修改另一个账本。
12. **AI 读取事实但不拥有事实。** AI 生成的行动必须经过确认并调用真实领域命令。
13. **聚合页面只做组合。** Today、History、Search、Trash 和 Growth 不成为竞争性写入 owner。
14. **个人文字默认受保护。** 关联 Task 或 Project 不代表允许其他能力读取完整正文。
15. **删除、归档和停用是不同语义。** 不得用一个通用状态替代全部生命周期。

## 9. 数据与技术约束

### 9.1 系统形态

```text
React + Vite SPA
→ HTTP /api/*
→ Hono API
→ Drizzle ORM
→ MySQL 8

Flyway SQL migrations 管理数据库演进
```

Web 与 API 只通过 HTTP 交互，不跨 workspace 直接引用后端源码。API 路由负责传输与校验；存在跨表事务或稳定领域规则时，由对应领域能力拥有业务逻辑。

### 9.2 数据原则

- 业务日期使用 `YYYY-MM-DD`；绝对时间使用 UTC 语义；
- 历史记录保存 `recordTimezone` 或相应业务日期快照；
- 财务金额使用整数分，不允许前端浮点累计；
- 数据库 SQL migration 是部署历史，Drizzle schema 是运行时映射；
- 已部署的历史 migration 不为修复当前环境而改写；
- 多表写入必须使用数据库事务；
- Web Query 是服务端快照缓存，表单草稿由各 Feature 本地拥有。

### 9.3 安全与隐私

- 除健康检查和认证入口外，业务 API 需要认证；
- 用户查询和写入按 `userId` 隔离；
- 密码不以明文保存，认证使用服务端 token 会话；
- 财务导出和恢复由用户主动触发；
- Quick Note、Journal 等私人正文不因来源关系自动暴露给其他领域；
- OpenAI API Key 只存在服务端环境，不发送到 Web 客户端。

## 10. 非功能需求

### 10.1 一致性与恢复

- 重复点击、网络重试和响应丢失不得重复创建时间、奖励、Task 或财务流水；
- 原子动作中任一步失败时整体回滚；
- 版本冲突返回明确的 409，不静默覆盖用户新数据；
- 页面刷新、浏览器前进后退和重新登录后，可从服务端恢复关键状态；
- 写作、Task、Quick Note 等编辑失败时保留用户草稿。

### 10.2 可用性

- 主要业务页必须提供 Loading、Empty、Error 和 Ready 状态；
- 桌面和移动端共享业务能力，但高频动作在移动端保持紧凑；
- Modal 支持 Escape 关闭、焦点约束和关闭后焦点恢复；
- 关键操作不只依赖颜色表达；
- 字体缩放、减少动效和语言设置在应用级生效。

### 10.3 可维护性

- AppShell 只负责路由和跨 Feature 组合，不拥有领域草稿；
- Feature 通过公开 surface 被消费，其他模块不得直接穿透内部实现；
- 不为单个功能提前建立通用平台或万能实体；
- OpenAPI、数据库 schema、migration、Web 类型和实现需同步审阅；
- 新的跨领域能力必须明确唯一 owner 和依赖方向。

### 10.4 验证要求

当前仓库的常规质量门槛包括：

- TypeScript typecheck；
- Web Vitest；
- API 单元/集成测试；
- 使用真实迁移后 MySQL 的数据库工作流测试；
- build 和 lint；
- 关键页面的浏览器证据脚本；
- `git diff --check`。

数据库语义不能只用 mock 或前端测试代替。移动端验收必须使用真实目标 viewport。

## 12. 产品指标

当前仓库没有稳定的线上行为分析基线，因此以下指标是后续应采集的产品指标，不应描述为已经达成：

### 12.1 核心使用指标

- 首次注册后完成“发布—接取—开始计时”的比例；
- 每周至少完成一次完整执行闭环的活跃用户比例；
- 接取任务中产生真实投入或完成事实的比例；
- Quick Note 后续被再次查看、加入灵感库或转成 Task 的比例；
- Finance 连续记账天数和月度对账完成率；
- 周/月回看页面的使用频率。

### 12.2 质量指标

- 重复操作导致的重复事实数量应为 0；
- 财务对账差异应可解释，无法追溯的余额变化应为 0；
- 关键写入失败后的草稿丢失率应为 0；
- 关键页面移动端遮挡和不可操作问题应为 0；
- 用户 A 数据出现在用户 B 会话中的数量应为 0。

## 14. 发布与变更原则

1. 新功能必须进入明确的领域 owner，不得把业务状态继续堆入 AppShell。
2. 新增聚合视图不得创建第二份领域真值。
3. 涉及数据库结构时使用当前 migration head 之后的新前向迁移。
4. 涉及接口字段、路径、鉴权或错误语义时同步更新 OpenAPI。
5. 涉及模块归属、数据真值或依赖方向变化时同步更新 `ARCHITECTURE.md`。
6. 涉及真实数据库语义时必须在隔离测试库完成迁移和集成验证。
7. 涉及移动端或真实交互时，必须补浏览器证据或自动化断言。
8. 完成当前需求和必要回归后停止，不把一次迭代扩张成无关重构。

## 15. 结论

Personal Workbench 当前已经不是概念验证，而是具备多个可独立使用领域的个人工作台：核心执行链、项目、习惯、生活记录、文字与灵感、成长、个人财务、搜索和数据维护均已有实际实现。

下一阶段的重点不应继续横向堆叠入口，而应完成三件事：

1. 把 Growth 视觉和现有产品体验收尾；
2. 把已经存在的局部 AI 能力收束成可追溯、可控成本的基础能力；
3. 建立真正的 Period Review，让现有事实形成长期复盘闭环。

任何后续扩展都应继续遵守当前产品最重要的原则：真实事实只有一个 owner，自动化不能替用户做未经确认的现实决定，个人数据必须可追溯、可恢复、可带走。
